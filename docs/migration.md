# 换机与故障恢复

## 先区分三种情况

- SSH 或手机断开：服务器与后台任务可能仍正常；重新连接并查询，不重复提交任务。
- 原实例关机再开机：磁盘可能保留，内存与进程已经终止；检查后先恢复 Mihomo 及代理环境，再重启 bridge，并从 checkpoint 决定是否恢复实验。
- 新建/释放/更换实例：按新环境重建；不能认为旧机器的 home、autodl-tmp、登录状态或 tmux 会自动出现。

AutoDL 官方说明中，`/root/autodl-tmp` 是实例数据盘，不能随系统镜像保存；`/root/autodl-fs` 面向同地区实例共享。重要材料需额外备份；不要把镜像等同于全部研究数据备份。[目录说明](https://www.autodl.com/docs/env/)

## 有计划的切换

| 阶段 | 操作 | 通过条件 |
|---|---|---|
| 1. 冻结新任务 | 暂停 heartbeat/cron，停止接受新实验 | 没有正在提交的新任务 |
| 2. 记录项目 | 更新 STATE；记录进程、revision、未提交文件、数据版本 | 下一步可由文件重建 |
| 3. 保存实验 | 按项目机制生成 checkpoint，将结果/数据复制到实例外 | 目标端数量、大小与关键哈希核验通过 |
| 4. 准备新实例 | 安装相同版本、恢复目录、单独验证 agent 登录 | 新实例尚未连接生产机器人 |
| 5. 停止旧桥接 | 正常停止旧 cc-connect，确认不再收消息 | 旧进程已退出；训练是否停另行处理 |
| 6. 保存最终会话 | 在会话不再写入后备份状态及所选 agent 会话 | 私密备份完整，可恢复 |
| 7. 新实例接管 | 载入凭证与白名单，启动唯一活跃桥接 | 手机收到包含新节点标识的回复 |
| 8. 验证恢复 | 核验项目状态、历史或新会话、任务去重、权限 | 验收清单相应项目通过 |
| 9. 退役旧机 | 确认备份与新机运行后，由用户决定释放 | 不由脚本自动删除或释放 |

回滚：先停止新节点，再恢复旧桥接。任何时刻避免同一个机器人在两台独立实例上同时接收。旧节点不可控时先确认它确实离线，必要时在飞书端轮换 App Secret 后只给新节点；轮换也会影响使用该凭证的其他连接，不能悄悄执行。

## 具体保存什么

1. **代码与未提交改动**：Git commit 只涵盖已提交内容。检查 `git status`；获授权后提交/推送，或私密保存明确的修改文件与补丁。新产生但未跟踪的文件也必须逐个处理。
2. **实验材料**：输入数据版本、配置、环境锁、checkpoint、输出与日志。不要仅复制文件名列表或 STATUS.json；在备份目标读取关键文件进行验证。
3. **桥接状态**：实际 `BRIDGE_STATE_DIR`（含 `config.<profile>.toml` 运行配置、选定模型和会话映射）及配置模板/profile、版本信息。聊天记录可能包含私密内容，不能上传公开仓库。
4. **agent 会话**：按所用 CLI 的实际 home/会话存储选择备份范围。Codex 默认 home 是 `~/.codex`，Claude Code 会话通常在 `~/.claude/projects`；先核对所装版本和实际文件，不宣称复制一个固定文件就必能跨版本恢复。整个 agent home 可能含凭证、日志和数据库，需停写后一致备份并按秘密保管。
5. **代理**：Mihomo 准确版本、完整私密配置、订阅/节点、选定策略缓存、专用 proxy.env 及启动入口。订阅 URL 本身可能是秘密，不进 Git。
6. **凭证**：单独保管，优先新机重新登录或注入；不随项目 Git 同步。重复使用同一个 refresh token 的多写者可能出现轮换冲突，不把复制登录缓存作为默认多机同步策略。

cc-connect 会话映射含项目名与绝对工作目录哈希。因此恢复历史尽量保持这两项和版本不变；不可保持时先开启新会话读取项目状态，不为追求聊天连续性手改数据库。

原机重启和换机都必须核对实际 session ID，再验证旧对话内容；从 STATE 新建对话是降级恢复，不能记为原会话恢复通过。操作细节见 [会话与认证设计](session-and-auth.md) 和 [代理恢复](proxy.md)。

## 故障时怎么判定

| 现象 | 先检查 | 恢复动作 |
|---|---|---|
| 飞书没回复 | 实例在线、bridge 进程、白名单、应用发布/订阅、出站连接 | 按层恢复，别先重装全部 |
| CLI 能回复，飞书不能 | App ID/Secret、本人 open_id、事件与发送权限 | 修平台配置 |
| CLI 自己也失败 | provider/模型名、账号权限、key、网络 | 修模型层再测桥接 |
| 重启后认证失败 | 服务运行用户、PATH、环境注入、凭证存储、过期状态 | 修启动环境或由用户重登 |
| Codex 不出现审批 | exec/app_server 的区别和当前 mode | 更换经测试的审批分支，不能默改 yolo |
| 卡片点击无反应 | card.action.trigger、发布版本、相关权限 | 先恢复纯文本，再单独联调卡片 |
| 新机历史不见了 | project name / 绝对路径 / CLI 会话 / provider | 先从 STATE 恢复任务，再排查历史 |
| 训练“似乎停了” | 实际进程、唯一任务 ID、日志时间、checkpoint | 证实退出且确认恢复点后再启动 |

桥接断线期间发出的指令不作为已接单证明。每项重要任务需要明确的任务 ID 和接单回执；没有回执时先查询状态，避免重复执行。
